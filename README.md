# dsh-coldread-cache

[English](./README.en.md) | **简体中文**

[![dsh-plugin](https://img.shields.io/badge/dsh--plugin-topic-2f6feb)](https://github.com/topics/dsh-plugin)

把正在写入的会话日志常驻在内存里解析，长会话不再越用越卡。

这是一个 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（DSH）插件。
它**不修改 DSH 安装目录里的任何文件**：挂载时在运行中的持久化后端实例上写入自有属性，
卸载时还原。

---

## 症状与根因

会话开得越久、轮次越多，界面就越卡：切换会话变慢、发一条消息要等、磁盘一直有读写。
关掉重开就好了——过一会儿又慢慢卡起来。

根因不是内存泄漏，是**整份冷读**：

1. DSH 把每个会话存成 `session.v4.jsonl.zstd`：可独立解码的 zstd 帧拼接，每帧一个
   JSONL 批次，首帧是头部。
2. JSONL 后端会缓存已解析的日志，但缓存**上限只有两条**，且以 stat 推导出的
   `revision` 作为键。
3. **每次追加都会改变这个 revision**，所以正在写入的会话几乎每次读都缓存未命中。
4. 未命中就是一次整份冷读：整个文件 `readFile` → 逐帧 zstd 解码 → 逐行 `JSON.parse`。

本机真实日志实测：

| 文件 | 事件数 | 整份冷读 |
| --- | --- | --- |
| 16 MB | 15 958 | 576 ms |
| 73 MB | 约 39 700 | 约 2 400 ms |

开销几乎全在 JSON 层，不在解压也不在磁盘：73 MB 的文件里 `JSON.parse` 约
1 750 ms、`JSON.stringify` 约 2 470 ms。

抓到的现场：一个开着长会话的宿主进程 **30 秒读了 846 MB**，峰值 61.6 MB/s，
30 秒内 37 477 次读操作；而刚启动的宿主基本是 0 MB/s。

## 这个插件做了什么

为每个会话保留**一个常驻解码器**，用的是后端同一套已发布的格式解码器，只做增量扩展、
不重建：

- 文件**没变** → 一次 `stat` 之后直接从常驻结果返回；
- 文件**变长了** → 只读新增的那段字节，解码后喂给常驻解码器追加；
- **其它任何情况** → 原样交给后端自身的读取逻辑，不猜、不凑。

实测：把真实追加产生的帧喂给一个已有的 16k 事件解码器，耗时**不到 1 ms**，
而同一份日志整份冷读是 **576 ms**，且扩展结果与整份解析深度相等。
已经发出去的事件对象在增长后**仍是同一批对象**，调用方不会看到抖动。

### 一个踩过的坑

后端在返回结果前会调 `freezeStoredEvents`，它**原地冻死**解码器持有的那个事件数组。
所以插件必须让常驻解码器保持未冻结，每次读**发一份冻结副本**出去。
否则第二次追加会直接炸：

```
Cannot add property 15953, object is not extensible
```

## 正确性

只有在能够证明「复用等价于整份解析」时才复用常驻结果：

1. 同一个文件——device + inode 相同，且路径相同；
2. 文件只增长，且头部帧的字节未变；
3. 常驻长度之后的每个字节都是完整、可独立解码的 zstd 帧（尾部撕裂就回退）；
4. 把这些帧喂给常驻解码器只会**新增行**，且格式解码器自身的关系约束仍然成立；
5. 新增行通过与后端读取逻辑**相同的** v4 行准入、存储事件校验与关系断言，
   并且上报的是**实际观测到的** revision。

任何一条无法证明就回退。所以最坏情况只是「和没装一样慢」，不会更慢，也不会给出
一份和整份解析不同的答案。

## 安装

插件由 profile 加载，并自带插入行：

```jsonc
// <profile>/cordis.patch.yml
- insert:
    - id: coldread-cache
      name: 'dsh-coldread-cache'
```

推荐用 dsh 自带的插件命令装：

```sh
dsh plugin --profile <name> add dsh-coldread-cache
```

手工挂载需要同时改三处，缺一处启动就会失败：

| 文件 | 需要什么 |
| --- | --- |
| `<profile>/package.json` | `dependencies` 里有本包 |
| `<profile>/package.json` | `dsh.profile.bundles` 里有 `dsh-coldread-cache` |
| `<profile>/cordis.patch.yml` | 上面那条 `insert` 行 |

挂载顺序不用管：插件先试 `ctx.get("sessionPersistence")`，服务还没起来就注册
`ctx.on("internal/service", …)` 等它出现。所以宿主**启动时自动生效**，不需要人工干预。

## 配置

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `enabled` | `true` | 允许从常驻结果直接返回 |
| `maxEntries` | `8` | 本进程常驻的会话数 |
| `maxResidentBytes` | `134217728` | 常驻源字节总量 |
| `statusFile` | `""` | 可选的实时诊断文件路径 |

前两项是进程的内存策略。后端自己那份两条的缓存**原样不动**。

这个预算是按**压缩后的源字节**算的，但你付的是**堆**。实测一份解析出来的日志约等于
源字节的 **8 倍**（202 MB 的会话在堆上约 1207 MB）：所以默认 128 MB 预算大约值 1 GB 堆。
`statusFile` 里的 `resident.heapEstimateBytes` / `heapRatio` 就是这份实时估算——比例由真实
冷读采样得到，不是写死的常数。内存宽裕的机器可以调大它。

**这个默认值试过调小，实测后撤回了。**直觉是「预算小一点省内存、行为不变」，但用真实会话
量了一遍（1 个会话在写、4 个在读）：

| 预算 | 常驻 | 常驻命中率 |
| --- | --- | --- |
| 16 MB | 35 MB | 14% |
| 32 MB | 35 MB | 14% |
| 64 MB | 35 MB | 14% |
| 128 MB | 99 MB | **53%** |
| 256 MB | 167 MB | **93%** |

原因：真正解决卡顿的那条路径（把「追加后立刻读」交给常驻解析扩展）**16 MB 就够**——因为
被写入的会话排在只被读的会话前面。预算再往上买的是**纯读**会话的常驻：翻历史、会话列表、
来回切会话。所以 128 MB 是「能服务一个真实工作集」的最小值；调小是拿一个实测到的功能退化
去换一个不是瓶颈的内存节省。

### 为什么会在长时间使用后变卡（已修）

扩展路径**每轮都会深冻结整条会话的事件图**：`Object.freeze` 要递归走到每个对象。
这本身是对的（冻结是为了和后端行为一致），但它在扩展时被套在了**全部**事件上，而不是
只套在新追加的那几个上。于是每轮都要重新走一遍整条会话——成本随会话变长而线性增长。
在 6 万事件的日志上实测：

| 每轮扩展的动作 | 耗时 |
| --- | --- |
| 冻结结果里的每一个事件（改前） | **191.7 / 199.5 ms**（两次） |
| 只冻结新追加的事件（改后） | **0.4 / 1.8 ms**（两次） |
| `concat` 本身（无法省） | 0.3 ms |

一个 100 轮的会话大约要为此花 **20 秒**纯冻结——这就是「用得越久越卡」的一个真实来源，
而且是插件自己引入的。修法有两条，互为保险：① 扩展时只冻结新事件；② `freezeStoredEvent`
遇到**已经冻结**的根就直接返回（已冻结的根意味着整棵图都冻结了，因为冻结永远是整图一次
完成的）。第 ② 条让第 ① 条即使漏掉某条路径也不会退化。门禁里有一条断言遍历扩展后的真实
结果、确认**每个**事件都深冻结，并且用一个故意留开口的对象证明这条断言**能真的报出问题**。

修完后的 A/B 中位数：**131 ms**（改前约 500 ms）。

### 淘汰顺序

常驻满了先淘汰谁，是按**读**的最近性吗？不是——那样在真实宿主上会失效。旁观会话的读取
本身就是一次冷读，冷读会让那条会话变成「最近使用」，于是**正在被写入**的那条会话反而被挤
出去，而「追加后立刻读」恰恰是本插件唯一的目标场景。实测：宿主连续跑 85 分钟、405 次读由
常驻服务、扩展次数 **0**，回退原因全是 `no-entry`。

所以规则改成：**被写入过的会话优先于只被读过的会话**。同级之间按最近读取淘汰，最后一条永
不淘汰。门禁里有一条专门的回归断言，并且用故障注入证明它能变红（把写入排名关掉，同一条
断言必须失败）。`resident.hot` 是当前被标记为「写入中」的会话数。

`statusFile` 是排查用的：写一份实时文档（心跳刷新），说明这份进程**实际装上了哪些钩子**、
命中了多少次、回退的原因分布。一个静默失效的插件比一个从没装上的插件更糟，所以留了这个
口子。

## 验证

```sh
pnpm run gate          # 验收门禁，跑真实 vendored 后端
pnpm run fault         # 故障注入：证明上面的门禁真的能变红
pnpm run perf          # 真实会话日志上的「追加后读取」A/B
pnpm test              # 依赖与安装机制探针

pnpm run probe:freeze  # 每轮全量冻结 vs 只冻结新事件（回归断言）
pnpm run probe:evict   # 旁观流量下常驻能否存活（回归断言）
pnpm run probe:budget  # 各预算档的常驻命中率（默认值就是靠它定的）
pnpm run probe:heap    # 常驻的堆开销（源字节 → 堆的换算比例）
```

`probe:*` 这几条是把 README 里的数字量出来的脚本，不是装饰：`probe:freeze` 和
`probe:evict` 都带断言，改坏了会 exit 1。它们需要真实会话：默认读 `$DSH_HOME\sessions`
（未设则 `$DSH_HOME` 必填），也可以用 `DSH_SESSIONS` 直接指到会话目录。

### 门禁

`GATE_GREEN checks=93 failures=0`（约 3.5 分钟）。门禁把**真实的 vendored 后端**跑两遍同一批
真实会话副本（一遍原始、一遍打上插件），深度比对结果，覆盖：语料、追加路径、尾部撕裂文件、
同长度改写、卸载还原、关闭常驻的对照组、**旁观流量下常驻的存活**，并包含一次**故意注入
错误答案的故障注入**——用来证明这个比对本身能失败。没有故障注入的绿色不算绿色。

`pnpm run fault` 单独跑 7 项故障注入，证明门禁的关键断言都能真的变红：
翻转一个字节让 vendored 摘要检查失败、少一个事件 / 多一个字段让读取比对失败、
关掉常驻后命中数必须为 0（否则性能断言就是自证）。同时门禁脚本自带互斥锁——
两实例同跑会污染同一份 fixture，锁让第二次运行直接拒绝而不是悄悄给出错误结论。

两棵 vendored 目录始终保持与出厂 SHA-256 字节一致
（`027803DDE72AAC7038253F0A8FF9FDCDBF0EB8CAD53ED26EFA3EC610F01587E7`），
门禁在每次运行的**开头和结尾**都断言这一点。

### 性能 A/B

在真实的约 90 MB 会话日志上，用后端**自己的写入路径**追加一个真实批次，再计量紧随其后
的那次读（也就是宿主每轮都要做的那次读），各跑 5 轮取中位数：

三次独立运行的中位数（同一份 ~90 MB 真实会话，每次 5 轮）：

| 追加后的一次读 | 运行 1 | 运行 2 | 运行 3 | 运行 4 |
| --- | --- | --- | --- | --- |
| 原始后端 | 2 928 ms | 4 232 ms | 5 972 ms | 2 930 ms |
| 挂插件但关闭常驻（对照组） | 5 244 ms | 6 436 ms | 6 493 ms | 5 744 ms |
| **挂插件** | **474 ms** | **410 ms** | **477 ms** | **509 ms** |

即 **5.8×–12.5×**。对照组就是这个断言自己的证明：同一段循环、同一个
后端类、同一个文件，只关掉常驻——它一点加速都没有，说明这个断言**能真的变红**。

### 去掉每轮全量冻结之后

上面那批数字是在**扩展路径还每轮深冻结整条会话**时测的。修掉之后（见「为什么会在
长时间使用后变卡」），同一份 fixture 又跑了两次：

| 追加后的一次读 | 运行 A | 运行 B |
| --- | --- | --- |
| 原始后端 | 8 417 ms | 2 893 ms |
| 挂插件但关闭常驻（对照组） | 6 959 ms | 4 682 ms |
| **挂插件** | **131 ms** | **88 ms** |

即 **22×–64×**。绝对值随机器负载浮动（原始后端自己两次就差 3 倍），所以结论看的是
倍数，而对照组是让这个倍数可信的东西。

> 注意：这里比的**不是**「同一个文件读两遍」。后端自己那份两条缓存已经能让重复读很快，
> 那样比什么都证明不了。真正会卡的是**读一份刚刚变长的日志**，所以 A/B 测的就是这个。

### 实机

单独冷启一份 profile 到另一个端口（不动正在用的宿主），什么参数都不给：

```json
{
  "backend": "session-persistence-jsonl",
  "installed": ["readStoredLog","decodeStoredLog","persistBatch","persistHeader","truncateTornTail"],
  "failures": {}
}
```

启动日志里零条插件错误。然后在界面上**纯 UI 操作**来回切换真实会话：

```
hits=4   ext=0  cold=1     ← 第一次打开
hits=5   ext=0  cold=2     ← 打开另一个会话
hits=9   ext=1  cold=3     ← 回到已打开的会话：靠「扩展常驻解析」服务，没有重新冷读
hits=11  ext=2  cold=4     ← 再一轮：又两次扩展
```

关键在最后两行：`extensions` 涨了，`coldParses` 没跟着涨。

### 真实宿主上发现的缺陷（已修）

上面这段是**短时间、来回切同一个会话**的情形，它掩盖了一个只在长时间使用下才暴露的问题。
在一台连续跑了 85 分钟、真实使用中的宿主上，状态文件是这样：

```json
"stats": { "hits": 405, "extensions": 0, "coldParses": 369,
           "fallbacks": 369, "reasons": { "no-entry": 369 } }
```

**405 次读由常驻服务，扩展 0 次，369 次回退全部是 `no-entry`。**也就是说：插件唯一的目标
场景（追加后立刻读）在真实使用里一次都没走通。原因就是上面「淘汰顺序」那节——按读的最近
性淘汰，会被旁观会话的冷读把正在写入的会话挤出去。这条缺陷是看实机计数器发现的，不是靠
测试发现的；修完才有「淘汰顺序」那节和对应的回归断言。

## 限制

- 快速路径只覆盖「按整帧增长」和「完全没变」。尾部撕裂、改写、截断、帧表重建都会回退。
- 常驻是**进程级**的，宿主重启后失效；插件会在挂载时重新安装。
- 第一次读永远是冷的（那一刻还没有常驻结果可用）。
- 后端自己那份两条的缓存不受影响，插件另有自己的字节数与条目数预算。
